# AI Coding 工程实践 SOP v1.0

> 想探索不会编程语言也能负责任的交付高质量产品的可能

***

## 0. 这份 SOP 的立场

### 0.1 一句话

> **AI 消除了「实现阻塞」，放大了「定义阻塞」。**&#x9636;段投入没有变少，只是从"想清楚怎么做"转移到"**想清楚怎样算做对**"。

### 0.2 五条设计原则

| **#** | **原则**         | **说明**                                                            |
| ----- | -------------- | ----------------------------------------------------------------- |
| P1    | **验收标准前置**     | 验收标准是贯穿需求→设计→执行→测试的**横向基线**，不是测试阶段的产物。它同时是需求的出口、设计的约束、执行的验收、测试的入口 |
| P2    | **证伪优先于完整**    | 不追求设计文档面面俱到，追求每条约束都**可证伪**。写不出"失败场景"的条款一律删除                       |
| P3    | **规约优先于提示词**   | 提示词一次性、随会话衰减；项目规约一次投入、每个任务自动继承，且**唯一不依赖个人水平**                     |
| P4    | **测试是执行的停止条件** | 测试与执行**短回路交替**（实现 → 独立测试 → 归因 → 修复），而非合并成一锅，更不是事后补                |
| P5    | **闭环必须有刹车**    | 反馈闭环的目的不是"把所有问题都回流"，而是**当回流成本高于问题价值时切断**。没有刹车的闭环就是进度黑洞            |

## 1. 角色与职责

| **角色**   | **职责**                    | **不可兼任的限制**            |
| -------- | ------------------------- | ---------------------- |
| 需求方      | 提出需求、给出**可判定的验收标准**、裁决 L3 | —                      |
| 需求评审人    | 跑需求 Checklist、复述需求        | **不得是提需求者本人**          |
| 设计负责人    | 产出设计、裁决 L2、维护 ADR         | —                      |
| 执行者      | 拆任务、装配上下文、派发、拦截 AI 输出     | —                      |
| 交叉验收人    | 同伴验收（≠实现者）                | **不得是实现者，不得是 AI 同一会话** |
| 用户/需求方验收 | 最终验收                      | **不得是实现者**             |

> ⚠️ 若组长一人身兼需求 / 设计 / 裁决（实验室常见），至少保证：**验收环节不由本人包办**，且 L2 裁决时限从 48h 放宽到**周窗口**。

## 2. 全流程总览

```
         ┌──────────────────── 横向基线：验收标准 ────────────────────┐
         │         （需求阶段定义，测试阶段原样落成用例骨架）          │
         ↓                ↓                ↓                ↓
   ① 需求  ──→  ② 设计  ──→  ③ 执行  ──→  ④ 测试 / 验收
      │            ▲            │                │
      │            │            └──────┬─────────┘
      │            │                   │ 发现问题
      │            │              先归因，不是先改
      │            │                   │
      │        L2 设计缺陷          L0 实现细节 / L1 环境噪声
      │            │                   │
      │            │              就地消化，不回流
      │            │
      └── L3 需求缺陷 ←───────────────┘
```

**纵向回边规则**：只有 L2 / L3 允许回流到上游；L0 / L1 就地消化。详见 §7。

### 各阶段产物与门禁

| **阶段** | **输入**    | **产物**                   | **出口门禁**                 |
| ------ | --------- | ------------------------ | ------------------------ |
| ① 需求   | 原始诉求      | 需求文档 + **验收标准**          | DoR（Definition of Ready） |
| ② 设计   | 需求文档      | 架构说明 + 接口契约 + 数据模型 + ADR | **Design Freeze**        |
| ③ 执行   | 设计 + 任务单  | 代码 + 测试 + PR             | 硬手段全绿 + 归因已记录            |
| ④ 测试验收 | 验收标准 + 代码 | 测试报告 + 验收结论              | DoD（Definition of Done）  |

## 3. 阶段一：需求 —— 把"怎样算做对"定义清楚

### 3.1 核心认知

> 人遇到模糊会来问；**AI 遇到模糊会静默补全**一个"最像的"答案，且写得自信、能编译、能跑。
> **人的失败是"卡住"，AI 的失败是"建成"。**&#x6240;以需求评审的价值从"防止返工"变成"**防止错误被优雅地固化**"。

### 3.2 需求模板（缺一项不予评审）

| **字段**       | **填写要求**                                  |
| ------------ | ----------------------------------------- |
| 一句话目标        | 谁 + 要什么 + 为什么                             |
| 范围 / **非范围** | 必须列出"这次不做"的 **≥3 条**                      |
| **验收标准**     | **≥3 条**，Given/When/Then 形式，**可被直接翻译成断言** |
| 约束           | 性能 / 成本 / 延迟，**写数字**（禁止"尽量快""足够好"）        |
| 依赖与假设        | 外部接口 / 数据 / 环境；未定的显式标 **"未定"**（不得留空）      |
| 异常与边界        | **≥3 条**（空值、超限、失败路径）                      |
| 提出人 / 评审人    | 评审人不得为空集                                  |

**验收标准写法示例**

```
✅ 好：给定 10 万条输入，检索返回 Top-10 的 P95 延迟 ≤ 200ms，超出则记录 warn 日志并降级返回 Top-5
❌ 差：检索要快，结果要准，异常情况要处理好
```

### 3.3 需求评审 Checklist（任一 No → 退回）

- [ ] 每条验收标准能否写出一个断言？

- [ ] 是否写了"不做什么"？

- [ ] 约束是否带数字？

- [ ] 外部依赖是否给出文档链接确认真实存在？（不得是 AI 回忆）

- [ ] 异常路径 ≥3 条？

- [ ] 术语是否有唯一定义？

- [ ] 是否标出"必须真机 / 实测才能验证"的项？

### 3.4 DoR ↔ DoD 锁扣（防止下游跑偏）

| **DoR（进入设计门槛）** | **对应 DoD（验收出口）**          |
| --------------- | ------------------------- |
| ≥3 条可断言的验收标准    | 每条标准有对应用例，且用例本身经人确认正确     |
| 列出非范围           | PR diff 无范围外改动            |
| 约束带数字           | 有对应性能 / 成本实测数字            |
| 外部依赖已确认存在       | 集成测试跑通真实依赖（**非 mock 全替**） |
| 异常路径清单          | 每条异常有用例覆盖                 |

### 3.5 硬性规则

> **验收标准变更走需求变更流程，测试不得自行增删。**

## 4. 阶段二：设计 —— 审可证伪的约束，不审代码细节

### 4.1 核心认知

看不出设计细节是事实，但不是放弃评审的理由。**要换的是评审对象，不是评审本身。**

> **AI 不知道你们的业务事实——这正是人的信息优势位。**

"AI 设计 + 换个 AI 再评审"的失效点是三个结构性同源：

| **同源维度** | **后果**                                            |
| -------- | ------------------------------------------------- |
| 同训练分布    | 两个模型对同一背景给出同一套"默认合理架构"，罕见约束（硬件时序、强一致、离线）被默认假设悄悄吞掉 |
| 同目标函数    | 生成方优化"自洽流畅"，评审方优化"同意一个合理的说法" → 互相背书               |
| 无上下文差    | 评审方看不到需求方原话、量级数据、硬件约束 → 只能做文本层挑刺                  |

**判定**：这条链路能发现"文档不完整"，**发现不了"断言是错的"**。而真正导致返工的从来是后者。

### 4.2 设计评审清单：可证伪约束表

| **评审项** | **通过判据（必须可证伪）**                              |
| ------- | -------------------------------------------- |
| 接口契约    | 能否构造一个**会失败**的调用？输入/输出/**错误语义**/幂等性是否写明      |
| 数据模型不变量 | 能否举出一条**必然违反它**的真实数据？唯一键 / 所有权 / 生命周期 / 删除级联 |
| 失败路径    | 依赖挂掉（超时 / 重试 / 部分失败 / 并发）时行为是否被**定义**        |
| 量级边界    | 数量级**改一位**，设计还成立吗                            |
| 非功能约束   | 能否被**量化并测出来**？一致性级别（强/最终）是否明确                |
| 选型退出成本  | 半年后想换这个组件，要动几处、有没有替身                         |
| 可观测性    | 出事第一眼看什么？没日志能否定位                             |

> 🔒 **铁律：任何写不出"失败场景"的条款一律删除。**"扩展性良好""高内聚低耦合"——AI 最爱产出，AI 评审也最难自查，因为它在语言上是自洽的。

### 4.3 前置决策 vs 可延后决策

> **凡是"改了要别人跟着改"的，前置；凡是"改了只影响自己"的，延后。**

**必须前置（后置 = 数据迁移或多方联动返工，代价 10 倍偿还）**

* 数据模型与所有权（表、主键、生命周期）
* 跨模块接口契约（含**错误语义**与**幂等性**）
* 一致性模型与事务边界（强一致 vs 最终一致）
* 权限 / 多租户隔离边界（安全类，**无后补窗口**）
* 外部选型（DB / 队列 / 框架）+ 退出路径
* 非功能目标数值（延迟 / 吞吐 / 成本上限）——**没有它就无法判定实现好坏**
* 可回滚性与灰度策略

**可延后（可增量迭代、可局部重构）**

* 模块内部结构、类划分、目录结构、命名
* 算法选型与性能优化细节
* UI / 交互细节与文案
* 依赖小版本、具体设计模式
* 单元测试的具体用例

### 4.4 Design Freeze 门禁

设计阶段出口必须产出三样东西，缺一不得进入执行：

1. `docs/conventions/api-contract.md` —— 接口契约（含错误码表）
2. 数据模型定义（含不变量声明）
3. ADR（Architecture Decision Record）—— 关键选型及**被否决方案的否决原因**

### 4.5 调研与内部知识库治理

> **知识库是减值资产，半衰期 6–12 个月。** 不加治理它会主动把 AI 拉回过时方案。

1. 每条知识必须带四个字段：`来源 / 验证日期 / 验证过的最小用例 / 失效条件`
2. 超 6 个月未被检索命中即标 deprecated，**移出检索池**
3. **必须收录负向知识**：本项目踩过的坑、被否决的方案及否决原因

→ 正向知识网上到处都是；AI 检索最缺的恰恰是"**这条我们试过，不行**"

4. ⚠️ **只有正向知识 + 无时效标记的知识库，比没有知识库更糟**——它会让 AI 更自信地重复你已经否掉的方案

## 5. 阶段三：执行 —— 装配上下文与拦截错误输出

### 5.1 核心认知

> "敲代码"确实被 AI 替代了；但"执行"没有——它只是换了形态：
> **从写代码变成装配上下文、划边界、定验收、拦截错误输出。**

AI 把写代码成本打下来了，把**判断对不对**的成本原封不动留给你，还因产出量大而**放大**。

被"完全替代了"这个说法掩盖掉的成本：

| **被掩盖项**                  | **后果**               |
| ------------------------- | -------------------- |
| 上下文装配（AI 只看见你喂的）          | 看不见的代码 = 重复实现、接口对不上  |
| 任务边界划分（AI 不会自己收窄）         | 一次改 20 个文件，无法 review |
| 验证成本（写快了，读和验没快）           | 产出速度↑，**吞吐未必↑**      |
| 技术债（AI 无全局记忆，就地打补丁）       | 同一逻辑 N 种写法           |
| 隐式依赖（并发/时序/副作用/配置）        | 单测过、集成挂              |
| **"看起来对"的代码**（规范、有注释、逻辑错） | **最难发现，review 成本最高** |

### 5.2 优先级：① 项目规约 ＞ ② 任务拆解 ＞ ③ 反幻觉硬手段 ＞ ④ 提示词

| **项**    | **投入** | **复用性**            | **判断依据**                    |
| -------- | ------ | ------------------ | --------------------------- |
| **项目规约** | 一次     | 每任务 / 每会话自动继承      | **唯一不依赖个人水平**；写不好提示词，但能照规约做 |
| 任务拆解     | 每任务    | 决定**失败半径**         | 粒度对了，错也错在小范围                |
| 反幻觉硬手段   | 每任务    | 最后一道闸              | 要在前两项之后才最有效                 |
| 提示词      | 每任务    | **一次性、不可复用、随会话衰减** | 放最后                         |

**​**

### 5.3 项目规约仓库结构

```
AGENTS.md                          # AI 必读入口
docs/architecture.md                # 模块划分 + 依赖方向
docs/conventions/api-contract.md    # 接口定义，改接口先改这里
docs/conventions/code-style.md      # 命名 / 目录 / 注释 / 提交格式
docs/conventions/error-handling.md  # 统一错误码 / 异常 / 日志
docs/forbidden.md                   # 禁止事项清单
docs/glossary.md                    # 术语表（消除命名漂移）
docs/decisions/ADR-0001-xxx.md      # 架构决策记录
docs/knowledge/                     # 内部知识库（负向知识优先）
scripts/check.sh                    # 一键 lint + typecheck + test
```

**`AGENTS.md` 五段，缺一即被绕过**

1. **动手前必读哪些文件**
2. **依赖方向**（如 `controller → service → repo`，禁止反向）
3. **必守约定**（错误类型、配置来源、禁止内联魔法值）
4. **禁止清单**（新增依赖 / 改公共签名 / 删测试 / 留 `// TODO` / 跨模块猜接口）
5. **完成定义**：`scripts/check.sh` 绿 + 新增测试 + 说明改动文件

### 5.4 任务拆解粒度（五条全满足才可派发）

1. 一段话讲清 **输入 / 输出 / 边界 / 验收**
2. 改动文件 **≤5**（新增除外）
3. 无需跨模块推断，涉及的接口在上下文中**可见**
4. 单一可验证结果
5. 预计 **≤1 次往返**，超了就再拆

**反例（粒度过大）**：「给用户模块加权限校验」

漂移路径：AI 自定义权限模型 → 改 12 个文件 → 新造的 `checkPermission()` 与既有 `rbac.ts` 的 `can()` 并存 → mock 单测全过 → 集成时两套逻辑冲突。

**正确拆法**：

① 定权限数据结构（types + 迁移）→ ② 实现纯函数 `can()` + 单测 → ③ middleware 接入（单文件）→ ④ 分批补路由（每批 ≤5 文件）

### 5.5 上下文装配规则

**必须放进上下文**

* 目标文件**全文**
* 直接调用方 / 被调用方
* 接口契约定义
* 该模块已有测试
* 相关规约片段
* **一条"照着写"的同类现成代码**（比任何风格描述都有效）

**必须排除**

* 整仓搜索结果
* 无关模块
* 过时文档
* 历史会话残留
* **你自己都没读过的文件**

### 5.6 任务派发模板

```markdown
# 任务 [一句话目标]

## 背景
[为什么改，2-3 句]

## 现有代码
- 目标文件：<path>
- 相关接口：<path#symbol>
- 参考实现：<path>（照此风格写）

## 需求
1. <行为 1>
2. <行为 2>
边界：空输入 / 超长 / 并发 / 失败时如何

## 约束
- 只改：<白名单文件>
- 禁止：新增依赖 / 改公共签名 / 删测试
- 复用：已有 <symbol>，不要重写

## 验收
- 命令：scripts/check.sh
- 新增用例：<path>

## 交付前（按顺序执行）
1. 先复述你理解的需求（≤5 行），我确认后再动手
2. 列出不确定点（≤3 条），并标注你的假设
3. 完成说明：改了哪些文件 / 每处为什么 / **哪些没验证**
```

### 5.7 反幻觉：硬手段优先

> 🔒 **原则：不要用软手段解决本可硬拦截的问题。**

| **类型** | **手段**                          | **性质**          |
| ------ | ------------------------------- | --------------- |
| 软      | 提示词强调、"不确定就说"、给示例               | **降概率，不可检测**    |
| **硬**  | 编译 / 类型检查 / lint                | 可拦截             |
| **硬**  | 既有测试仍绿 + 必须新增测试                 | 可拦截             |
| **硬**  | diff 只落在白名单文件                   | 可拦截             |
| **硬**  | 依赖锁未变（禁新增依赖）                    | 可拦截             |
| **硬**  | **动手前先复述需求 + 列假设清单**            | **动手前**拦截（成本最低） |
| **硬**  | 换模型 / 新会话独立实现同一任务，对 diff **求交** | 可拦截             |
| **硬**  | 引用接口须给 `file:line`，不存在即幻觉       | 可拦截             |

⚠️ 最后一类"**看起来对**"的代码（规范、有注释、逻辑错）硬手段拦不住，只能靠 §5.8 人工接管 + §6.4 交叉验收。

### 5.8 必须人工接管（命中任一）

- [ ] 并发 / 事务 / 幂等 / 分布式时序

- [ ] 权限、鉴权、密钥、支付、数据删除

- [ ] 改公共接口签名或 schema

- [ ] 同一处 AI 已失败 2 次

- [ ] "和 X 一样但……"而你看不懂 X

- [ ] diff 里出现你叫不出名字的 API

- [ ] 热循环 / 大数据量 / N+1 等性能敏感路径

> Python / JS 等动态语言、硬件驱动、前端视觉、无测试老仓库：上述阈值**一律调严**。

## 6. 阶段四：测试与验收 —— 测试是执行的停止条件

### 6.1 核心认知

> 与执行"密不可分"这个直觉是对的——测试应是执行的**停止条件**而非事后环节。
> 但"合并"≠ 在同一个会话里边写边测：**那会让 AI 用实现去解释自己的 bug**。
> 正确形态是**短回路交替**：实现 → **独立**测试 → 归因 → 修复。

### 6.2 测试层级与插入时机

| **层级**   | **由谁写**             | **何时插入**         | **通过标准**        |
| -------- | ------------------- | ---------------- | --------------- |
| 单元       | AI 起稿，**人定 oracle** | 与函数同批提交，进 PR 前必有 | 断言可溯源到需求，且含反向用例 |
| **契约**   | **人定契约**，AI 写实现与测试  | 设计冻结后，**先于联调**   | 调用方与实现方过同一份契约   |
| 集成       | AI 起稿，人审断言来源        | 模块联调前            | 真实依赖或等价替身       |
| 系统 / E2E | 人定场景，AI 写脚本         | 功能集完成后、演示前       | 走通主流程 + 关键异常流   |
| 回归       | 累积沉淀                | 每次合并 + 每晚        | 历史用例全绿          |
| 非功能      | 人定阈值                | 里程碑节点            | 指标达阈值           |

**测试先行（先写测试再让 AI 实现）在 AI 下成本极低，以下三种情况必须先行：**

1. **修 bug**：先写一个复现失败的测试再改——这是唯一能证明"修好了"且防回归的手段
2. 需求已含明确验收标准（边界值、错误码、格式）→ 直接落成参数化用例
3. 重构 / 换模型实现前，先用现有行为锁住测试

**不必强行**：探索性原型、纯 UI 表现、一次性脚本。

### 6.3 如何自证测试（最硬的一问）

#### oracle 可靠性排序

```
需求/验收标准        ← 最可靠
  ↓
外部真值（RFC、第三方契约、真实数据）
  ↓
已知正确参考实现 / 黄金文件
  ↓
不变量 / 性质
  ↓
❌ 被测代码本身      ← 陷阱
```

> ⚠️ **AI 生成测试最大的陷阱：与实现同源。**&#x5B83;照抄实现逻辑写断言 → **永远通过，覆盖率还很高** → 那不是测试，是**实现的镜像**。

#### 自证手段

| **手段**        | **做法**                                    | **适用边界**                               |
| ------------- | ----------------------------------------- | -------------------------------------- |
| **变异测试**      | 故意改坏实现（翻转比较符、`≤`→`<`、删判空、改返回值），测试**必须变红** | 只在**核心纯逻辑模块**（数十\~数百行、少 IO）抽检；不设 CI 门禁 |
| **元变 / 性质测试** | 精确 oracle 算不出时用：排序无关性、编解码往返、幂等性、增删守恒      | 写性质比写用例难，仅用于解析器/转换器/排序检索类              |
| **人工抽审断言来源**  | 每 5\~10 个 AI 用例，挑 1 个**手算**预期值对照          | 全场景适用                                  |
| 覆盖率           | 只用于**定位未覆盖分支**                            | ⚠️ **永远不是正确性证据**——AI 很容易刷到 90% 而全是弱断言  |

工具参考：mutmut (Python) / Stryker (JS) / Hypothesis (Python) / fast-check (JS)

#### 用例评审 Checklist（进 PR 门禁）

- [ ] 每个断言常量可追到需求条款 / 规格 / 外部真值，禁止与实现同表达式

- [ ] 至少一个"应当失败 / 抛异常"的反向用例（AI 默认只写 happy path）

- [ ] 边界：空 / 0 / 1 / 上限 / 非法类型 / 超时

- [ ] 关键模块抽样变异，测试必须红

- [ ] 用例独立、可重复、不依赖执行顺序

- [ ] 失败信息可读（期望 X，实际 Y）

### 6.4 AI 测试可信度判据

> **一句话判据：预期结果能否在不看被测代码的情况下独立写出来？能** → AI 可独立完成；**不能** → 人先写预期，AI 只做执行与批量化。

| **维度** | **可交给 AI**                   | **必须人工**                     |
| ------ | ---------------------------- | ---------------------------- |
| 类型     | 样板用例、fixture、数据构造、参数化展开、回归脚本 | **oracle 定义、验收标准、通过/失败判定**   |
| 风险     | 低风险纯计算 / 工具函数                | 资金、权限、删除、不可逆写、对外接口           |
| 外部事实   | 内部自洽逻辑                       | 业务规则、第三方契约、法规、真实数据分布         |
| 稳定性    | 已冻结接口                        | 需求未定部分（**AI 会把临时行为固化成"标准"**） |

> 🔒 **AI 不得自评"通过"**——必须由独立 runner 执行。

### 6.5 失败处理

| **情形**            | **动作**               |
| ----------------- | -------------------- |
| 阻塞主流程 / 数据损坏 / 安全 | **立即停，立即修**          |
| 同一处 AI 连修 2 轮未果   | 停手转人工，回设计层找因         |
| 非阻塞边缘 bug         | 进 backlog，批量统一处理     |
| 失败源于需求 / 设计未定义    | **不在执行层修**，走 §7 反馈路由 |
| 偶发 flaky          | 隔离标记（**不禁言**），单独立项   |

> 🔒 **硬规则：一个 PR 内失败点 >3 个，或修复轮次 >2 轮 → 停止边测边改，转复盘。**&#x5269;余问题记为 **Known Issues** 交付，不无限调试。

**换会话防污染**

* **必须换**：连修 2 轮失败 / 会话已堆积大量试错 / 需要换范式级方案（旧会话会把 AI 锁死在错误路径上）
* **不要换**：仅缺局部上下文——换会话会丢掉隐性约束
* **不要裸换**：先产出"**干净上下文包**"再开新会话

→ 需求摘要 + 相关设计原文片段 + 最小复现 + **明确的旧误区警告**（"勿再用 X 方案，因为…"）

→ **把脏上下文翻译成干净约束，而不是丢掉上下文**

### 6.6 DoD（完成的定义）

一张卡，全绿才算完成：

- [ ] 用例全绿

- [ ] oracle 已溯源到需求条款

- [ ] 关键分支已覆盖

- [ ] 文档同步更新

- [ ] 观测日志就位

- [ ] 回归全绿

- [ ] 交叉验收通过

### 6.7 验收的五个必备项

| **项**            | **要求**                                                |
| ---------------- | ----------------------------------------------------- |
| **谁验收**          | 自测 → 同伴交叉验收 → 需求方/用户验收，**三者不可由同一人（或同一会话）包办**          |
| **验收标准来源**       | **必须在需求阶段定义死**，形式为"给定输入 → 可观测输出"，最好直接是可执行用例           |
| **非功能验收**        | 性能 / 并发 / 安全 / 成本阈值。AI 默认**不写超时、不限流、不校验权限**           |
| **回归确认**         | CI 全量回归 + 主干保护 + 关键路径冒烟清单。AI 改动波及面广，**人眼 review 看不见** |
| **Known Issues** | 遗留问题必须显式记录，不得静默略过                                     |

## 7. 反馈闭环：归因 → 分级 → 回流 → 重新下达

### 7.1 第一步永远是归因，不是改代码

> 执行期冒出来的"错误"，绝大多数不是执行问题，而是**上游输入的错误在执行期显形**。
> 执行只是第一个"必须落地、无法含糊"的环节，所以它背了锅。

| **归因三问**              | **归属与动作**                                 |
| --------------------- | ----------------------------------------- |
| 规约/文档里有答案，只是 AI 没看没守？ | **执行问题** → 补上下文、收紧规约，就地修                  |
| 需要新信息才能答（业务规则、边界取舍）？  | **需求问题** → 停下，回阶段一，**不准猜**                |
| 能答，但答案会影响其他模块 / 接口？   | **设计问题** → 回阶段二，改 `api-contract.md` 再派新任务 |

**配套纪律**

* **同一处返工 ≥2 次 → 强制升级归因**，不允许第 3 次"再让 AI 试试"
* **归因结论必须落回文件**（规约 / api-contract / 需求），**不能留在会话里**——否则同坑必再踩

### 7.2 分级判定表

| **级别**      | **触发信号**              | **典型例子**              | **回流载体**                  | **裁决人**  | **时限** |
| ----------- | --------------------- | --------------------- | ------------------------- | -------- | ------ |
| **L0 实现细节** | 局部代码问题，不动对外契约         | 命名、内部算法微调、函数拆分        | **不回流**，就地修 + commit note | 执行者      | 立即     |
| **L1 环境噪声** | 依赖 / 工具 / 环境导致        | 版本冲突、CI 挂             | 环境工单，**不入设计层**            | 组长       | 当天     |
| **L2 设计缺陷** | 契约 / 数据模型撑不住需求、非功能不达标 | 缺字段导致 N+1；接口无幂等导致重复扣款 | **DCR 设计变更单** + 更新 ADR    | 设计负责人    | 48h\*  |
| **L3 需求缺陷** | 语义空白或矛盾，多种实现都"合理"     | 权限模型未定义、边界场景无答案       | **需求澄清卡** → 需求方           | 需求方 + 组长 | 本周窗口   |

> ⚠️ **L1 单独列出很关键**：实际项目里超过一半的"执行发现问题"是环境噪声，**混进设计层会直接把闭环灌死**。
> \* 组长身兼多职时放宽到周窗口。

### 7.3 DCR 设计变更单模板

```markdown
# DCR-0042

- 所属模块：
- 级别：L2 / L3
- 复现场景（可执行）：
- **推翻了哪条设计假设**：        ← 必填，不填不予受理
- 影响面（涉及哪些契约）：
- 拟变更 diff：
- 验证方式：
```

> 🔒 **不写明"推翻了哪条假设"的 DCR 不予受理。**&#x8FD9;一条同时解决了知识沉淀：每条被推翻的假设就是一条**你们自己产出的、AI 语料里没有的负向知识**（回流到 §4.5 知识库）。

### 7.4 重新下达：禁止全量重发

> **全量重发必然漂移**——AI 会重新"理解"全局，用一套新的隐含假设**覆盖掉你已经验证过的部分**。

**正确姿势 = 基线快照 + 增量变更单**

1. 把给 AI 的输入拆成两块：
   * **① 不变的约束指纹**：接口契约、数据模型、已生效 ADR 的固定 Section，**标注版本 hash**
   * **② 差异块**：用 diff 明确标注 `NEW / CHANGED / DEPRECATED`
2. 显式声明：**"未列出的部分一律维持 v0.x 不变"**
3. **反向复述校验**：要求 AI 先输出"我理解的变化清单"，**人对齐后才许写码**→ 这一步是防漂移的**单点防火墙**，成本极低

### 7.5 防震荡

| **机制**   | **规则**                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------ |
| **批量窗口** | L2 不即时逐条处理，每日 2 个固定裁决窗口（如 10:00 / 16:00）统一批处理                                                          |
| **熔断阈值** | 同模块 **7 天内第 3 次 L2**，或同一 DCR 引发**回归 > 2 次** → 强制停工，转**人工设计评审 30 分钟**，产出 §4.2 的可证伪约束清单，**而不是继续打 AI 补丁** |
| **例外通道** | 阻塞性 / 安全类问题（数据丢失、越权）跳过窗口，即时处理                                                                          |

> **核心判断**：闭环的目的不是"把所有问题都回流"，而是**让回流的成本高于它修复的问题之价值时切断**（L0/L1 就地消化），并且给无限循环装一个**物理刹车**。

## 10. 本 SOP 的局限与适用边界

1. **技术栈差异**：强类型 + 有测试基建的栈（TS / Go / Java / Rust）硬手段拦截率最高；Python / JS 动态特性、硬件驱动、前端视觉、无测试老仓库，硬手段覆盖不到，"看起来对"的代码占比显著更高，§5.8 阈值要调严。
2. **项目类型差异**：一次性原型 / 研究型代码请把测试要求**大幅降级**；重 IO 的 Agent 类项目先把**契约测试 + 黄金数据回放**补齐，收益远大于追覆盖率。
3. **阈值是经验量级，不是定律**：48h / 7 天 / 2 次 / ≤5 文件 / ≤1 次往返——全部需要按你们的项目节奏校准。`<5 文件` 是**保守起点**，熟练后可放宽。
4. **变异测试 / 性质测试的成本**：只在**数千行以内、核心逻辑为纯函数**的模块划算，不要全项目铺开。
5. **角色假设**：本 SOP 假设存在"技术负责人"做 L2 裁决。若组长一人身兼多职，需按 §1 放宽时限并保证验收独立。
6. **未经你们真实代码库验证**：以上为方法层建议，具体工具链（mutmut / Stryker / Hypothesis / fast-check）需按语言栈落地。
