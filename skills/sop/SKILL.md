# SOP Entry

Define correctness through requirements, review important judgments, implement the smallest complete change and deliver real evidence. Read [shared boundaries](references/common.md) first. Follow the user's communication language; the English instructions do not require English replies.

## Start from the actual task

1. Read applicable project rules, existing requirements and design, relevant code and uncommitted changes. Recover the real goal, authorization, responsibilities, progress and outstanding validation. Missing templates do not prevent read-only investigation.
2. Recover goal/non-goals, observable acceptance, permitted code/data/environment changes, validation approach and responsible people from existing records. Investigate available facts before asking. Refer consequential ambiguity to the responsible human; an unanswered assumption is not approval. Do not request the same valid authorization again.
3. Distinguish drafting, review and implementation permission. A clear-looking document not yet reviewed is not an approved baseline. Reuse valid review evidence; inspect missing or changed parts, not the whole process again.
4. Load the skill needed now. A clear, authorized task with valid requirements review and sufficient reviewed decisions may go straight to execution; do not force a tour of every stage or invent new documents.

| Need | Skill | Next action |
| --- | --- | --- |
| Raw request, consequential ambiguity, acceptance gaps or requirements not yet reviewed | [requirements](../sop-requirements/SKILL.md) | Clarify, investigate and complete requirements review |
| Necessary design not yet reviewed, unfamiliar capability, important choice, public contract or data decision | [design](../sop-design/SKILL.md) | Research, choose and review the simplest complete solution |
| Valid reviewed requirements/design and implementation authorization | [execution](../sop-execution/SKILL.md) | Plan dependencies, establish the baseline, implement and self-test |
| Validation, cross-acceptance or delivery | [verification](../sop-verification/SKILL.md) | Check the acceptance basis, actual evidence and responsible acceptance |
| Problem at any stage, blocked validation, resumption or handoff | [recovery](../sop-recovery/SKILL.md) | Diagnose, route decisions, update the basis and close with evidence |

If installing over an existing setup, switching versions/forms, or encountering conflicting legacy entries, read [the upgrade procedure](references/upgrade.md) before changing files or starting affected business work. This branch is not required for fresh projects or unrelated read-only investigation.

## Project adoption and scale

Installing or discussing the kit does not adopt the workflow or authorize business changes. Reuse one project entry describing rule/requirement locations, responsibilities, permission boundaries, checks and current progress. Verify actual host loading; a declaration is not proof. Identify material rule conflicts and seek human resolution rather than activating conflicting workflows together.

Do not impose directories, templates, plans, meetings or a state system merely to demonstrate compliance. A small task can keep its basis, review conclusions, decisions and evidence in one record. Multi-person, dependent or cross-session work needs a persistent plan with predecessors, owners, acceptance, validation and status. Keep one authoritative location per task status, blocker and decision; summarize by reference.

The main use is requirements-driven full-stack feature delivery and cross-module iteration. Local fixes reuse valid reviewed baselines. Exploration defines the question, authorized operations and exit condition; prototype output needs appropriate review and verification before production delivery.

## Resources and reporting

- Resolve resources from this skill's directory, not the user's working directory. Invoke the host's actually discovered skill names and namespaces; if native invocation is unavailable, read the linked file instead of inventing a command.
- Load only what is needed. Installed skills are read-only resources; project records belong in established project locations.
- Report what changed, why, applicable acceptance, actual results, unresolved items and next responsibility. Missing necessary evidence means partial completion; passing tests is not product acceptance.

Example: read-only project exploration needs no document bundle. A small authorized link fix can reuse the existing reviewed documentation contract and check affected links; a new unreviewed feature cannot skip review because its description looks complete.
