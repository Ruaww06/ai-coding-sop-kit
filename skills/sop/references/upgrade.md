# Upgrade Without Mixing Workflows

Use only when installing over an existing SOP setup, switching versions/forms, or finding conflicting legacy entries. This is an Agent procedure, not an automatic migrator or permission grant. A fresh project does not need a migration record. Read the applicable installation guide from the same source version.

## Inspect before changing anything

Within the selected project and authorized installation scope, read applicable `AGENTS.md`, `CLAUDE.md` and their explicit rule references. Inspect the current host's actual skill locations and selected plugin source. Check legacy entries even when they are outside the new destination. Do not scan the whole home directory or follow symlinks outside scope; report unreadable or unresolved entries as unverified, not absent. Other-host copies are information, not current-host loading evidence or permission to modify them.

Identify the origin using declared versions, content and available published source comparisons—not directory names alone. Unknown, modified or mixed origins need a difference preview, not a guessed conversion. Preserve task records, customization, licenses, failure counts and outstanding validation. Old B/H/S or HOLD records remain historical evidence; they do not become current approval, a passing result or a reset count.

## Preserve v4 entry and project continuity

The five v3 skill names, plugin namespace, project/local-plugin forms and `common.md` / `upgrade.md` paths remain available. v4 adds `sop-requirements`; do not treat it as an unexpected leftover. A v2 skill with the same name is not the v4 implementation: compare its full content and linked resources. `sop-startup` and v2 extra references/templates remain retired; preserve filled-in project records, not their obsolete active rules.

v4 restores explicit requirements/design review, dependency planning and progress, and feedback decisions written into the basis before verified closure. Reuse existing valid review and authorization evidence for unchanged parts. For unreviewed material, review missing or affected decisions before dependent implementation; do not require a full rewrite. An upgrade is not retroactive approval and must not convert drafting, a v3 confirmation or model agreement into a human review. Preserve prior approval within its actual scope, failure counts, blocked items and outstanding validation. Installing new skills never starts business development or approves its completion.

## Preview a complete switch

List the current entry, target source/version, affected files and rule clauses, retained customization, retired active entries, required permissions, verification and recovery approach. Inspect rules embedded in project entry files as well as links; replacing a link does not remove an old rule body. Do not retain conflicting old clauses under a generic "custom" label or remove them without a human decision.

- **Independent checkout / local plugin:** use a separate complete source instead of overlaying files or resetting a modified checkout. Check project references and old project/user skills that could still win discovery. Switching the plugin path alone is insufficient when those remain active. Do not edit global settings or clear host caches as part of this procedure.
- **Copied project skills:** compare the entire installed SOP group, including extra files. Copying over existing directories does not remove retired skills, assets or references. Plan removal or retirement of the identified obsolete entries, not the host's whole skills directory. Stage a complete new group outside all host discovery paths; do not add a second active SOP group.
- **Legacy project documents:** preserve historical documents and records. Update only authorized active references and conflicting rule clauses. An archive is inactive only when the host no longer discovers it and project rules no longer require it. Do not delete `docs/sop/` wholesale.

Only proceed with the complete affected switch authorized. Installation-only permission is not permission to rewrite project rules, delete old entries or discard customization. If an active conflict cannot be resolved, stop the affected upgrade before overwriting shared files. Existing valid authorization need not be requested again.

## Check loading before retiring the only working entry

Confirm the new source is complete and readable, its resource links work, and the host's supported loading mechanism can use it. If possible, verify in an isolated discovery context without activating both versions in the real project. If the host cannot verify the new entry without first retiring the old one, obtain an explicit reversible switch plan preserving the old entry outside discovery; keep the upgrade pending until new loading is actually observed. Do not claim success or silently remove the only usable entry on file-presence evidence.

A host without native discovery may use an explicitly approved stable file-reading path; read the entry and required resources and report native discovery as not applicable. Do not use this exception to conceal a native discovery failure. Do not start another model process, weaken permissions or incur model charges without the corresponding authorization.

## Execute, verify, resume

1. Recompare files with the approved preview immediately before writing. New edits, changed origins or scope differences stop the affected step for a revised preview. Do not overwrite them using an old plan.
2. Apply only the authorized coherent switch. Preserve the old baseline or approved backup outside discovery; never copy business records into a versioned installation or erase them during cleanup. Do not use destructive resets or broad directory deletion.
3. Reread every affected active entry and referenced rule. Verify current-host loading resolves to the target source, resource links work, retired skills are no longer discoverable, no required references point at removed files, conflicting rule bodies are resolved and customization/history remain intact. Host refresh or restart may be needed; report loading pending until observed.
4. Report file installation, host loading and project rule switching separately as unchanged, pending, partial or verified. A verified switch requires all applicable checks, not just copied files or a changed plugin path. It does not establish business validation or final acceptance.
5. On failure, preserve the actual state and evidence, stop affected business execution and use only the approved recovery plan. Do not automatically roll back over new edits. On interruption, inspect current files and valid authorization again; continue only remaining authorized steps. A matching completed installation is a no-op, not a reason to rewrite files or repeat approvals.

Keep any necessary preview and result in the project's existing record location; do not create a migration database. Unknown failure counts stay unknown. Resume business work only when its applicable rules, authority and baseline are clear.
